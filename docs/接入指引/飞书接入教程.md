# 飞书接入教程：Windows、Codex 与桌面交互卡片

本文介绍在 Windows 上通过飞书使用 cc-connect，并启用本机 Codex 桌面会话通知和问题卡片回答。基础连接采用飞书长连接，无需公网服务器、域名或端口映射。

教程对应本仓库包含桌面回复补丁的版本，相关源码自提交 `ce3259b9` 起提供。操作命令使用 PowerShell；示例中的路径、项目名和账号标识需按实际部署填写。

## 1. 接入后可以做什么

| 使用场景 | 操作方式 | 处理对象 |
| --- | --- | --- |
| 在飞书下发新任务 | 向机器人发送普通消息 | cc-connect 项目中的 Codex 会话 |
| 接收桌面执行结果 | 在 Codex 桌面端正常工作 | 本机所有主会话的完成、问题和错误通知 |
| 回答桌面正在等待的问题 | 在飞书问题卡片中选择或填写，再点击「提交答案」 | 原 Codex 桌面会话、原来的活动轮次 |
| 使用文字回复桌面问题 | 发送 `/answer 问题编号 答案` | 编号对应的桌面问题 |
| 回复完成消息中的纯文字提问 | 引用新的「回复完成」通知并发送文字 | 在原桌面会话开始下一轮 |
| 处理桌面权限审批 | 查看飞书通知后，回到桌面审批 | 原工具权限请求 |

普通飞书消息进入 cc-connect 管理的会话。回答桌面问题时，使用对应的问题卡片、`/answer`，或引用带通知编号的新完成通知，以便将答案送回准确的桌面会话。旧通知没有引用绑定时会明确拒绝，不会启动普通 Agent。

Codex Hooks 属于官方提供的扩展机制；通过本机内部通信接口回填桌面问题，是本仓库提供的可选集成，支持范围见第 9 节。

## 2. 准备环境和路径

### 2.1 前置条件

- 飞书账号，以及可以创建或管理机器人的飞书开发者账号。
- 本机已安装并完成认证的 Codex CLI；在 PowerShell 中执行 `codex --version` 应成功。
- 使用桌面通知和问题回填时，安装并运行 Codex 桌面端。
- Node.js 18 或更高版本、npm；源码编译还需要 Go 1.25 或更高版本。
- 本仓库源码，以及可访问飞书开放平台、模型服务和依赖下载站点的网络。

检查本机命令：

```powershell
go version
node --version
npm --version
codex --version
```

### 2.2 本教程使用的路径

| 项目 | 示例 |
| --- | --- |
| 源码目录 | `E:\CompanyProject\cc-connect` |
| 程序文件 | `E:\Tools\cc-connect\cc-connect.exe` |
| cc-connect 配置 | `%USERPROFILE%\.cc-connect\config.toml` |
| 飞书普通任务工作目录 | `E:\cc-connect-workspace` |
| 桌面集成脚本目录 | `%USERPROFILE%\.codex\cc-connect-notify` |
| cc-connect 项目名 | `desktop-codex` |

在本次 PowerShell 窗口中定义变量：

```powershell
$repoDir = 'E:\CompanyProject\cc-connect'
$ccExe = 'E:\Tools\cc-connect\cc-connect.exe'
$ccConfigDir = Join-Path $env:USERPROFILE '.cc-connect'
$ccConfigFile = Join-Path $ccConfigDir 'config.toml'
$bridgeDir = Join-Path $env:USERPROFILE '.codex\cc-connect-notify'
$nodeExe = (Get-Command node.exe -ErrorAction Stop).Source

New-Item -ItemType Directory -Path (Split-Path -Parent $ccExe) -Force | Out-Null
New-Item -ItemType Directory -Path $ccConfigDir -Force | Out-Null
New-Item -ItemType Directory -Path 'E:\cc-connect-workspace' -Force | Out-Null
```

后续代码块沿用这些变量。新开 PowerShell 窗口后，需要重新定义。

已有安装应复用现有程序路径、项目名和脚本目录。例如，项目名 `wechat-codex`、脚本目录 `wechat-notify` 可以继续用于飞书，无需为改名重新安装或重新信任 Hooks。

## 3. 编译包含交互卡片功能的程序

基础飞书接入也可使用官方发行版；本教程包含桌面问题卡片，因此使用本仓库源码构建的程序。

先构建嵌入式管理页面，再编译 Go 程序：

```powershell
Set-Location -LiteralPath $repoDir

Push-Location -LiteralPath (Join-Path $repoDir 'web')
try {
    npm install --ignore-scripts --no-audit --no-fund --package-lock=false
    if ($LASTEXITCODE -ne 0) { throw '安装前端依赖失败' }

    npm run build
    if ($LASTEXITCODE -ne 0) { throw '构建前端失败' }
}
finally {
    Pop-Location
}

$buildCommit = git rev-parse --short HEAD
go build -tags goolm -ldflags "-s -w -X main.version=local-desktop-cards -X main.commit=$buildCommit" -o $ccExe ./cmd/cc-connect
if ($LASTEXITCODE -ne 0) { throw '编译 cc-connect 失败' }

& $ccExe --version
```

确认版本输出包含 `local-desktop-cards`。如果目标程序已经在运行，先按第 11 节停止并备份，再替换文件。

后续统一使用 `& $ccExe` 调用该程序，便于确认扫码配置、后台任务和桌面通知使用的是同一个版本。仅将补丁提交到仓库，不会自动替换已安装的程序。

## 4. 创建 Codex 项目并扫码接入飞书

### 4.1 准备配置文件

新部署时，在 `$ccConfigFile` 对应的文件中写入以下基础配置。已有配置时，将项目合并进去，并保留其他项目和全局设置。

```toml
language = "zh"
shell = "powershell.exe"

[[projects]]
name = "desktop-codex"

[projects.agent]
type = "codex"

[projects.agent.options]
work_dir = "E:/cc-connect-workspace"
backend = "exec"
mode = "yolo"
```

这里的 `work_dir` 用于从飞书下发的普通任务。桌面问题回复仍进入原桌面会话，并使用原会话的目录。

示例采用 `yolo` 模式，允许访问全机并跳过审批和沙箱。`exec` 后端的模式含义如下：

| 模式 | 行为 |
| --- | --- |
| `suggest` | 只读沙箱，不弹出交互审批 |
| `auto-edit`、`full-auto` | 允许写入工作目录，不弹出交互审批 |
| `yolo` | 跳过审批和沙箱，允许全机访问 |

### 4.2 执行扫码配置

```powershell
& $ccExe feishu setup --config $ccConfigFile --project desktop-codex
```

1. 使用手机飞书扫描终端显示的二维码。
2. 按飞书页面提示完成机器人创建和授权。
3. 返回终端，等待配置完成。
4. 记录机器人名称，后续在飞书中搜索该名称。

如果终端二维码不便扫描，可保存二维码图片：

```powershell
& $ccExe feishu setup --config $ccConfigFile --project desktop-codex --qr-image "$env:TEMP\cc-connect-feishu-qr.png"
```

首次扫码流程会写回目标项目的飞书凭证；通常也会预配机器人权限和事件。是否完整生效，以开放平台的应用配置和实际消息验证为准。

### 4.3 关联已有机器人

已有机器人的情况下，可以执行：

```powershell
& $ccExe feishu bind --config $ccConfigFile --project desktop-codex --app 'cli_YOUR_APP_ID:YOUR_APP_SECRET'
```

将占位值替换为应用凭证。该参数可能进入终端历史，相关记录应按凭证文件管理。也可在配置文件中填写以下平台部分：

```toml
[[projects.platforms]]
type = "feishu"

[projects.platforms.options]
app_id = "cli_YOUR_APP_ID"
app_secret = "YOUR_APP_SECRET"
enable_feishu_card = true
```

凭证属于飞书开放平台应用，不能使用群自定义机器人的 Webhook 地址代替。

## 5. 核对开放平台配置

打开 [飞书开放平台](https://open.feishu.cn/)，使用创建机器人的账号进入对应应用。若提示「无权访问」，先核对浏览器当前账号以及该账号是否拥有应用管理权限。

### 5.1 机器人能力与可用范围

1. 在应用能力中确认已启用机器人。
2. 设置应用名称和机器人名称。
3. 首次绑定阶段，将应用可用范围限定为预期使用者。
4. 在版本管理中确认配置已发布；企业应用按组织要求完成审批。

### 5.2 消息权限

基础私聊需要接收消息和以机器人身份发送消息的权限。按开放平台界面核对：

| 权限或能力 | 标识或说明 |
| --- | --- |
| 读取机器人单聊消息 | `im:message.p2p_msg:readonly` |
| 以应用身份发送消息 | `im:message:send_as_bot` |
| 获取用户基本信息 | `contact:user.base:readonly`，用于显示用户信息 |
| 群内被提及时接收消息 | 使用群聊时按需启用 `im:message.group_at_msg:readonly` |
| 读取未提及机器人的群消息 | 仅在需要群历史共享等功能时启用 `im:message.group_msg` |

本教程以私聊为目标；桌面问题回复桥接也绑定到指定私聊。卡片发送和更新需要应用具备相应消息能力，接口返回缺少权限时，依据错误详情补充并发布。

### 5.3 消息事件与卡片回调

在「事件与回调」中分别检查两个标签页：

| 标签页 | 接收方式 | 需要订阅的内容 |
| --- | --- | --- |
| 事件配置 | 使用长连接接收事件 | 接收消息：`im.message.receive_v1` |
| 回调配置 | 使用长连接接收回调 | 卡片回传交互：`card.action.trigger` |

分别保存，按后台要求创建版本并发布。普通消息能回复，只能证明消息链路可用；卡片按钮还需要回调链路可用。

保持 `enable_feishu_card = true`。设置为 `false` 会关闭平台卡片能力，无法发送本教程的桌面问题卡片。

## 6. 验证基础连接并绑定接收者

### 6.1 前台启动

```powershell
& $ccExe -config $ccConfigFile
```

日志中应出现配置加载成功、`platform ready` 且 `platform=feishu`，以及 `cc-connect is running` 等信息。

在飞书中找到机器人并发起私聊，发送：

```text
只回复：连接成功
```

收到「连接成功」后，基础的飞书 → cc-connect → Codex → 飞书链路成立。

### 6.2 获取用户和会话标识

在同一个飞书私聊中发送：

```text
/whoami
```

记录返回的：

- `User ID`：形如 `ou_...`。
- `Chat ID`：形如 `oc_...`。
- `Session Key`：形如 `feishu:oc_...:ou_...`。

使用 `/whoami` 实际返回的完整值。用户 Open ID 属于具体应用，换机器人后应重新获取。

在目标平台的配置中补充绑定用户：

```toml
[projects.platforms.options]
app_id = "cli_YOUR_APP_ID"
app_secret = "YOUR_APP_SECRET"
enable_feishu_card = true
allow_from = "ou_YOUR_USER_ID"
```

这里是修改已有的 `[projects.platforms.options]`，不要在同一平台中重复声明该表。`admin_from` 控制其他特权命令，桌面问题回复不需要为此添加管理员权限。

前台运行时按 `Ctrl+C` 停止，重新启动后验证 `/whoami` 和普通任务仍能使用。若收到访问拒绝，核对 `allow_from` 是否填入了当前应用下的用户 ID。

## 7. 配置后台运行与登录启动

前台验证完成后，先停止前台实例，再安装后台任务：

```powershell
& $ccExe daemon install --work-dir $ccConfigDir
& $ccExe daemon status
& $ccExe daemon logs -n 50
```

Windows 会创建名为 `cc-connect` 的计划任务，在当前用户登录时后台运行。安装输出中的 `Binary` 应等于 `$ccExe`，`WorkDir` 应指向存放 `config.toml` 的目录。

如果该任务已经存在，完成配置和程序备份后，可重新安装到当前路径：

```powershell
& $ccExe daemon install --work-dir $ccConfigDir --force
```

任务启动后，再发送一次「只回复：连接成功」，确认后台任务能够找到 Codex CLI 和原有认证。该登录任务运行于用户会话；用户未登录、电脑休眠或关机时，无法接收或回填桌面问题。

## 8. 安装桌面通知与问题卡片

完成基础接入后再配置本节。只需要从飞书调用 Codex 时，可直接使用第 10 节的常用命令。

### 8.1 复制配套脚本

```powershell
New-Item -ItemType Directory -Path $bridgeDir -Force | Out-Null

$bridgeFiles = @(
    'notify.mjs',
    'desktop-answer-command.mjs',
    'desktop-answer-store.mjs',
    'desktop-answer-ipc.mjs',
    'desktop-question-cards.mjs',
    'desktop-notifications.mjs'
)

foreach ($name in $bridgeFiles) {
    Copy-Item -LiteralPath (Join-Path $repoDir "integrations\codex-desktop\$name") -Destination (Join-Path $bridgeDir $name)
}
```

这些文件必须放在同一个目录。已有部署更新前先备份该目录，再替换对应脚本。

### 8.2 设置通知目标

在脚本目录生成 `settings.json`，先将 `sessionKey` 替换为第 6 节记录的完整值。已有项目名不同的，也要同步修改 `project`。

```powershell
$bridgeSettings = [ordered]@{
    ccBinary = $ccExe
    project = 'desktop-codex'
    sessionKey = 'feishu:oc_YOUR_CHAT_ID:ou_YOUR_USER_ID'
    codexHome = Join-Path $env:USERPROFILE '.codex'
    stateDir = Join-Path $bridgeDir 'state'
    logFile = Join-Path $bridgeDir 'notify.log'
    answerDir = Join-Path $bridgeDir 'questions'
    questionCards = $true
}

$settingsPath = Join-Path $bridgeDir 'settings.json'
[IO.File]::WriteAllText($settingsPath, ($bridgeSettings | ConvertTo-Json), [Text.UTF8Encoding]::new($false))
```

| 字段 | 含义 |
| --- | --- |
| `ccBinary` | 带桌面卡片补丁的程序完整路径，与后台运行版本一致 |
| `project` | cc-connect 中实际存在的项目名 |
| `sessionKey` | 指定机器人私聊的完整会话标识 |
| `codexHome` | 当前用户实际使用的 Codex 配置和会话目录 |
| `stateDir` | 已成功发送的通知去重记录 |
| `logFile` | 通知发送日志 |
| `answerDir` | 问题编号、卡片绑定和提交状态记录 |
| `questionCards` | 为 `true` 时发送桌面异步问题卡片 |

该文件无需填写飞书 App Secret；凭证仍由 cc-connect 的配置管理。

### 8.3 配置 cc-connect 的回复处理器

将以下配置作为**顶层数组表**加入 `config.toml`，与 `[[projects]]` 同级。将示例 Node 和脚本路径替换为 `$nodeExe` 与 `$bridgeDir` 对应的实际绝对路径。

```toml
[[hooks]]
event = "desktop.answer"
type = "command"
command = "& 'C:/Program Files/nodejs/node.exe' 'C:/Users/YOUR_USER/.codex/cc-connect-notify/desktop-answer-command.mjs'"
```

这段命令按配置中的 PowerShell 执行。`desktop.answer` 必须只有一个精确匹配的命令处理器；消息正文由程序作为 JSON 标准输入交给脚本。

若项目单独设置了 `shell`，该项目也应使用与上面命令语法一致的 PowerShell。配置完成后执行：

```powershell
& $ccExe daemon restart
& $ccExe daemon logs -n 50
```

### 8.4 配置 Codex 用户级 Hooks

Codex 用户级 Hooks 文件为 `%USERPROFILE%\.codex\hooks.json`。使用用户级配置，使本机各个桌面主会话都能触发通知。

先从仓库模板生成带实际路径的待合并文件：

```powershell
$templatePath = Join-Path $repoDir 'integrations\codex-desktop\hooks.example.json'
$hookTemplate = Get-Content -LiteralPath $templatePath -Raw | ConvertFrom-Json
$notifyScript = Join-Path $bridgeDir 'notify.mjs'
$notifyCommand = "powershell.exe -NoProfile -NonInteractive -Command `"& '$nodeExe' '$notifyScript'`""

foreach ($event in $hookTemplate.hooks.PSObject.Properties) {
    foreach ($rule in $event.Value) {
        foreach ($handler in $rule.hooks) {
            $handler.command = $notifyCommand
            $handler | Add-Member -NotePropertyName commandWindows -NotePropertyValue $notifyCommand -Force
        }
    }
}

$readyHooksPath = Join-Path $bridgeDir 'hooks.ready.json'
[IO.File]::WriteAllText($readyHooksPath, ($hookTemplate | ConvertTo-Json -Depth 12), [Text.UTF8Encoding]::new($false))
```

合并步骤：

1. 若现有 `hooks.json` 存在，先备份，并保留其中已有的规则。
2. 打开 `hooks.ready.json`，将五类事件下的新规则加入现有文件的对应数组。
3. 若同一条通知命令已经配置过，更新原规则即可，避免重复添加。
4. 若之前没有 `hooks.json`，可将待合并文件完整复制为该文件。
5. 保存后，在 Codex 桌面端进入 **Settings → Hooks**，或使用输入区提供的 **Review hooks** 入口，审阅并信任这五项命令。

仅保存配置文件不足以启用未受信任的 Hooks；修改定义后也需要按桌面提示重新审阅。

五类事件的作用：

| 事件 | 通知内容 |
| --- | --- |
| `Stop` | 一轮最终回复，正文最多约 2600 字符 |
| `PreToolUse`，匹配 `request_user_input` / `request_user_input_async` | 待回答问题；符合条件的异步问题生成卡片 |
| `PermissionRequest` | 工具权限请求，提示回桌面审批 |
| `PostModelRequest`，状态为 `failed` | 模型请求错误；原任务可能继续重试 |
| `PostToolUse` | 可识别的工具错误或非零退出码 |

模板使用 `async = true`，通知脚本输出 `{}`，用于发送提醒。是否覆盖某类事件，仍取决于当前桌面版本是否触发该 Hook。

## 9. 验收交互卡片

### 9.1 验收顺序

| 步骤 | 操作 | 通过标准 |
| --- | --- | --- |
| 1 | 在桌面会话中完成一轮普通任务 | 飞书收到包含该会话信息的完成通知 |
| 2 | 在桌面发起一个带选项的异步问题 | 飞书收到有选项、输入框和「提交答案」的卡片 |
| 3 | 只选择选项或输入文本 | 答案尚未提交，原问题仍待回答 |
| 4 | 点击「提交答案」 | 原桌面会话收到对应答案并继续执行 |
| 5 | 查看原卡片 | 卡片显示绿色「已提交」，包含答案并移除输入控件 |
| 6 | 用新问题验证自由文本 | 自由文本能到达原桌面会话，并更新卡片 |
| 7 | 对已提交编号重复发送 `/answer` | 拒绝重复提交，原桌面不出现第二份答案 |

测试时可在桌面明确要求：

```text
请调用 request_user_input_async 提出一个带选项的测试问题，
本轮保持运行，等待我从飞书卡片回答后再继续。
```

是否产生可回填的问题，以实际调用的工具为准。测试过程中先从飞书提交；桌面端同时回答会使原卡片失效。

填写自由文本时，即使选择了选项，也优先提交自由文本。卡片输入最多 1000 字符；文字备用命令最多 8000 字符：

```text
/answer Q-12AB34CD56EF 你的答案
```

问题编号位于卡片底部。多个会话、多个问题各自使用对应的卡片或编号。

### 9.2 回复完成消息中的纯文字提问

模型可能直接在最终回复里提问，没有调用 `request_user_input_async`。这类内容通过「回复完成」通知发送，此时桌面轮次已经结束。

新版通知底部包含 `N-...` 通知编号和引用回复提示。在飞书直接引用这条新通知，填写文字并发送，桥接会在原桌面会话开启下一轮，沿用原来的模型、目录和权限。

通知及对应绑定记录需在同一版本程序下生成。升级前的旧通知、已回复通知、会话已有更新、桌面正在执行任务或无法读取引用原文时，会明确拒绝，防止进入普通 Agent。此功能仅支持文字，不接受引用消息中的命令或附件。原问题卡片仍通过「提交答案」处理。

验证时引用一条新通知发送「只回复：引用回复成功」，检查答案出现在原桌面会话，并确认飞书收到引用回复回执；随后再次引用旧通知发送相同文字，应被拒绝。

### 9.3 当前支持范围

- 卡片回填支持本机 Codex 桌面主会话的 `request_user_input_async` 问题。完成通知的引用回复则用于在原会话开始下一轮。
- 卡片回填要求原问题所属轮次仍在运行；引用完成通知要求原会话已空闲且通知对应最新完成轮次。两者都要求原会话仍在桌面打开。
- 问题编号有效期为 24 小时，但轮次提前结束时会立即无法继续回填。
- 阻塞式 `request_user_input`、桌面权限审批和登录授权，需要回到桌面处理。
- CLI 会话、子代理和其他电脑上的会话不在通知范围内。
- 提交结果不明确时停止自动重发，需要到桌面确认；同一问题使用一个入口完成回答。

本机内部通信适配已在 Windows 桌面版本 `26.1103.7773.0` 验证。桌面应用更新后，应重新验证一个新问题，不能将内部接口视为长期稳定接口。

## 10. 日常使用与排查

### 10.1 常用命令

飞书私聊命令：

| 命令 | 用途 |
| --- | --- |
| `/help` | 查看当前可用命令 |
| `/new` | 新建 cc-connect 管理的会话 |
| `/current`、`/list` | 查看当前会话或会话列表 |
| `/stop` | 停止 cc-connect 当前任务 |
| `/mode`、`/reasoning` | 查看或调整 Agent 模式和推理强度 |
| `/whoami` | 查看当前应用下的用户和私聊标识 |
| `/answer 编号 答案` | 回答对应的桌面问题 |

`/new`、`/stop` 等普通命令作用于 cc-connect 管理的会话；桌面问题桥接只提供针对待回答问题的回复。

PowerShell 管理命令：

```powershell
& $ccExe daemon status
& $ccExe daemon logs -n 80
& $ccExe daemon restart
& $ccExe daemon stop
& $ccExe daemon start
```

### 10.2 日志和状态文件

| 文件 | 检查内容 |
| --- | --- |
| `%USERPROFILE%\.cc-connect\logs\cc-connect.log`，或后台安装输出的日志路径 | 平台连接、普通消息、卡片回调和桥接调用 |
| `$bridgeDir\notify.log` | 通知是否发送成功、是否被过滤或去重 |
| `$bridgeDir\answer.log` | 回答是否提交、被拒绝或结果未确认 |
| `$bridgeDir\questions\Q-*.json` | 问题绑定、有效期和提交状态 |
| `$bridgeDir\questions\notifications` | 完成通知与原桌面轮次、飞书消息 ID 的绑定及回复状态 |
| `$bridgeDir\state` | 成功通知的去重记录 |

提交成功时，问题记录为 `status: submitted`；`confirmedInDesktop: true` 表示已在桌面状态中观察到该回复。`notify.log` 中 `status: sent` 只表示发送链路成功，验收卡片回答还要确认桌面接收及原卡片状态。

### 10.3 常见现象

| 现象 | 排查方向 |
| --- | --- |
| 飞书搜不到机器人 | 应用发布状态、可用范围、当前飞书账号 |
| 开放平台提示无权访问 | 是否使用应用创建者账号，或是否具备应用管理权限 |
| 普通消息无回复 | 后台状态、`im.message.receive_v1`、消息权限、`allow_from`、Codex 认证 |
| 前台能用、后台不能用 | 后台安装时记录的程序路径、PATH、用户身份和配置目录 |
| 普通消息正常，桌面没有通知 | 五项用户级 Hooks 是否加载、启用并受信任，Node 和脚本路径是否正确 |
| 桌面问题只有文字通知 | 是否实际调用异步问题工具、是否运行带补丁的程序、`questionCards` 和 `answerDir` 是否配置 |
| 卡片按钮无反馈 | 已发布的 `card.action.trigger`、回调接收方式、后台程序版本 |
| 引用完成通知被拒绝 | 是否为新版生成的带 `N-...` 编号通知；原会话是否空闲、无新轮次且仍在桌面打开 |
| 引用后出现其他任务的工具消息 | 正常新版路由不会启动普通 Agent；检查是否仍运行旧程序，先用单独的 `/stop` 停止误启动的飞书任务，再核对程序路径 |
| 卡片提示信息无效 | 卡片是否来自旧程序；新建问题验证，必要时使用卡片编号和 `/answer` |
| 提示原轮次结束或问题已回答 | 到桌面检查原问题，按当前状态继续任务 |
| 提示无法取得桌面状态或接口不兼容 | 原会话是否打开、桌面是否仍在运行，以及更新后的内部接口是否需要重新适配 |
| 发送错误提示包含路径不存在 | 查看通知中的会话、目录和工具输出，返回该会话排查对应任务的文件路径 |

正常的表单回调会包含按钮名 `desktop_question_submit`、`action/code/token` 等定位字段和表单字段。当前补丁使用 `behaviors.callback.value` 回传定位信息，相关日志仅记录字段名。

### 10.4 限流与失败通知

飞书消息发送和卡片更新受应用 API 权益及对应接口限流约束，以租户后台和实际接口错误为准。个人微信的消息配额不适用于飞书。

当前通知脚本在成功发送后去重，没有持久化重试队列，也不会自动重放失败通知。遇到限流或网络错误时，先检查日志及平台返回信息，再在桌面确认任务状态。

## 11. 更新、备份与停用

### 11.1 更新程序或脚本

1. 记录当前程序路径、版本和后台任务安装信息。
2. 停止后台任务，并确认对应程序实例退出。
3. 备份当前程序、`config.toml`、`settings.json`、脚本目录和 Codex Hooks 配置。
4. 替换程序或脚本，保持六个 `.mjs` 文件来自同一版本。
5. 若程序路径发生变化，更新 `ccBinary` 并重新安装后台任务；脚本路径或 Hook 定义变化时，重新审阅并信任。
6. 启动后台，重新验证普通回复、完成通知、选项卡片和文本卡片。

检查实例时可按实际可执行文件路径筛选：

```powershell
Get-CimInstance Win32_Process -Filter "Name='cc-connect.exe'" |
    Where-Object { $_.ExecutablePath -eq $ccExe } |
    Select-Object ProcessId, ExecutablePath, CreationDate
```

旧版本后台管理可能遗留子进程。确认新版本生效时，同时核对进程路径、启动时间和日志中的平台就绪信息。

配置备份包含凭证，问题记录包含题目、选项和卡片绑定令牌，应保存在本机私有位置，不纳入 Git 提交。

### 11.2 停用桌面集成

在 Codex 桌面端的 Hooks 设置中禁用对应五项通知规则，并从 cc-connect 配置中移除精确的 `desktop.answer` 处理器。桌面问题仍可在桌面回答。

若只将 `questionCards` 改为 `false`，异步问题改用带编号的文字通知，`/answer` 处理器可以继续保留；后续完成通知也不再建立新的引用回复绑定。

需要移除 Windows 登录启动时，执行：

```powershell
& $ccExe daemon uninstall
```
